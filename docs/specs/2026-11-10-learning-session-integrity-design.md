# 学习模式的会话完整性设计

日期：2026-11-10　状态：待批准

## 意图

学习模式（设备所在 Group 的 `interface = "learning"`）靠一组锁约束学生的会话：dconf 锁、藏起的应用、执行层堵住的终端与文件管理器。
这些锁由**以学生身份运行的程序**去读、去遵守；而这些程序同时也读学生家目录里的个人配置，学生能用浏览器的"另存为"往家目录写文件。
2026-11-10 已按读取方逐个修了三处（用户的 environment.d、Flatpak 的用户导出目录、`~/.pam_environment`），每次审查都再找出一处，
说明缺的是模型而不是补丁。David 要的是好的设计：先写清学习模式要保证什么，每一条只在一个地方实现，以后出现新的绕过方式先问
"它违反了哪一条"。

## 学习模式的四条不变式

1. **模式只有一个权威来源，任何时刻都不比实际执行的锁更松。** agent 决定模式；对外发布的 `session-mode` 与 dconf 锁按固定次序写，
   读到的模式永远不会比生效的锁更宽松。所有读模式的地方只读这一份。
2. **学习模式的会话每次都从已知状态开始。** 学生登录时、在任何属于学生的进程启动之前，root 把家目录收拾成"只留保留清单里的"，
   其余个人配置挪走；不留下上一次会话的用户 systemd 管理器。
3. **会话中能运行什么有边界。**（第二期，本设计只写范围。）
4. **完全模式照 Ubuntu 原样。** 1–3 只作用于学习模式的设备；老师用完全模式的设备，定制能力一点不少（David 11-10：按设备区分，
   以后有需要再加按账号区分）。

## 目标（第一期：不变式 1、2、4）

- 学生往家目录里放的、能改变下一次会话的东西（环境变量、自启动、systemd 用户服务、D-Bus 服务、shell 启动脚本、shell 扩展、
  默认应用、用户 Flatpak……），下一次在学习模式设备上登录时都不起作用——**包括今天没想到的读取方**，因为不在保留清单里的都不在了。
- 模式的发布与锁的写入之间没有"锁已生效、模式还写着 full"的窗口。
- 完全模式的设备与还没有设置的设备行为不变。

## 非目标

- 不做会话中的执行控制（不变式 3，第二期）。第一期之后仍存在的已知缺口：会话中存一个 `.desktop` 启动器到
  `~/.local/share/applications`，它马上出现在应用列表里、点了就运行（见"第二期"）。
- 不改锁定应用（kiosk）账号与访客：它们已经是临时账号，每次会话都是新的家目录。
- 不做按账号区分模式。
- 不防 root 级攻击（`/usr` 只读且有完整性校验，本来就不在此列）。

## 反目标（做到了也算失败）

- 学生自己的文件（下载、文档、桌面上的文件）、Chrome 的资料（书签、登录状态、扩展）、学校装的 Flatpak 应用的数据被删或丢。
- 清理出错导致学生登录不了（一个 bug 让全校学生进不去，比学生绕开限制严重得多）。
- root 在学生可控的目录树里操作时被符号链接或挂载点骗去动系统文件。
- 完全模式设备上的任何行为变化。

## 方案

| 方案 | 内容 | 取舍 |
|---|---|---|
| A. 按读取方逐个堵（现状） | 每发现一个读取方就加一个过滤 | 永远补不完；已连续三轮被审查找出新的一处 |
| **B. 登录前按保留清单收拾家目录（选定）** | root 在登录钩子里只留清单里的东西 | 一处实现，覆盖未知读取方；管不到会话中的手段 |
| C. 执行控制（不变式 3） | 学习模式只许运行批准的程序 | 最根本，但允许清单要在 VM 上反复磨；作为第二期，与 B 互补 |
| D. 挂载遮挡 | pam_namespace 把危险路径盖成只读空目录 | 仍是按路径列举（黑名单），且要两处命名空间一致，kiosk 那次已吃过苦头 |

B 是保留清单（白名单），新软件读新路径时不用改它；C 解决 B 解决不了的会话中手段。David 11-10 认可这个方向。

## 设计

### 不变式 1：模式的发布次序

- 权威来源仍是 agent；对外的发布物仍是 `/var/lib/mastersos-public/session-mode`（root 0644，`learning` 或 `full`），
  agent 私有的 `exec-block-mode` 不变。
- 改写入次序（今天 desktop 步骤先写 dconf 锁，最后才由 `exec_block::apply` 写 `session-mode`）：
  - **收紧**（新模式是 learning）：先写 `session-mode = learning`，再写 dconf 锁、覆盖、执行层堵法。
  - **放开**（新模式是 full）：先撤 dconf 锁、覆盖、执行层堵法，全部成功后最后写 `session-mode = full`；任何一步失败就不写，
    `session-mode` 留在 learning（往锁的方向落），由下一轮重试。
- 这要把今天的 `exec_block::write_mode`（一次写 `exec-block-mode` 与 `session-mode`，写失败也照样收敛，复审 T13 R2）拆开：
  `exec-block-mode` 照旧；`session-mode` 改由 desktop 步骤按上面的次序单独写，且**只对它**反过来——放开时写不成就停在 learning。
- 放开时"全部成功"只指与锁有关的几步：dconf 锁、`Hidden=true` 覆盖、D-Bus 覆盖、执行层堵法。网页应用图标下载失败之类与锁无关的错误
  照常回报，不挡 `session-mode = full`（否则一张图标下载失败就让老师的设备每次登录都被收拾）。
- 读模式的一方只读 `session-mode`，规则统一：文件不在 = 还没有设置 = full；`full` = full；其余（含读不出、认不出）= learning。
  - 2026-11-10 两个环境生成器里"有 dconf 锁文件就按 learning"的判断删掉（它是补次序漏洞的补丁）。
  - `/usr/lib/mastersos/browser-wait` 今天把"不是 learning"都当放开，改成同一条规则。
- 测试：用记录调用顺序的假 runner / 假文件系统，断言两个方向的写入次序与失败时 `session-mode` 的值。

### 不变式 2：登录前收拾家目录

**在哪里做：** `mastersos-agent pam-session`（root，PAM 会话段最前面，早于 `pam_env`、`pam_mkhomedir`、`pam_systemd`）。
对 `SessionAction::Enqueue` 的普通账号（SSO 学生与本机账号），且 `session-mode` 是 learning 时做；访客与 kiosk 账号不做（已是临时的），
完全模式不做。

**保留清单**（以家目录为根；其余的都挪走）：

| 保留 | 原因 |
|---|---|
| 家目录顶层所有**不以 `.` 开头**的条目 | 学生自己的文件（Downloads、Documents、Desktop 等） |
| `.config/google-chrome` | Chrome 资料：书签、登录状态、扩展（Chrome 由企业策略管着） |
| `.cache/google-chrome` | 只为不每次重下缓存 |
| `.pki/nssdb/cert9.db`、`.pki/nssdb/key4.db` | Chrome 的证书库与私钥（不留 `pkcs11.txt`：它让 Chrome 加载模块） |
| `.config/dconf` | 用户的 dconf 库（壁纸、语言、输入法等个人设置；该锁的键由系统锁住） |
| `.local/share/keyrings` | 密钥环（保存的密码） |
| `.var/app` | 学校装的 Flatpak 应用的数据 |
| `.config/monitors.xml` | 外接屏幕的排布与缩放 |
| `.local/state/wireplumber` | 音量与默认输出设备 |
| `.config/gtk-3.0/bookmarks` | 文件选择框侧栏的书签 |

清单写在 Rust 里一处常量，每一项带一行为什么留。**加项的规则**（实施者与以后的人照此判断，不必每项回头问）：只收纯数据或偏好文件；
凡是会被当作"要运行的程序"、"要加载的代码或扩展"、"要读的环境变量或配置目录"的（启动器、自启动、服务定义、脚本、扩展、
`mimeapps.list` 之类），一律不收。每次加项在代码审查里按这条看。

**已知代价：** 学生在 Chrome 里自己安装的网页应用，启动器（`~/.local/share/applications/chrome-*.desktop`）每次登录后没了；
应用本身还在 Chrome 里（`chrome://apps` 打得开）。启动器是可执行的入口，按加项规则不收；学校指定的网页应用由 agent 放在系统目录，不受影响。

**怎么收拾（耗时只与保留清单的长度有关）：**
- `.config`、`.local`、`.cache`、`.var`、`.pki` 这几个容器目录：在家目录里新建一个空的同类目录，把这个容器里在保留清单上的子项逐个
  `rename` 进去，然后把旧容器整个 `rename` 进 `/home` 下现有的回收目录（`homes::trash`，root 0700，与家目录同一文件系统），再把新的
  `rename` 到原名。学生在容器里放了多少东西都不影响耗时；容器里的挂载点随旧容器一起挪走（目录里含挂载点可以改名）。
- 家目录顶层其余以 `.` 开头的条目（`.profile`、`.bashrc`、`.pam_environment`、`.mozilla`……）：逐个挪进回收目录。这一步要列目录，
  上限放宽（实施者按 `PAM_CMD_TIMEOUT` 定），正常家目录只有十几项。
- 全部经 `safefs`：逐级 `openat`、`O_NOFOLLOW`、只处理属主是这个用户的家目录；符号链接被当作普通条目挪走，从不跟随；容器本身若是
  挂载点（`rename` 报 `EBUSY`）就跳过并记一笔。
- 挪进回收目录的由现有的 `HomeCleanupJob` 删除；登录路径上不做递归删除。

**上一次会话留下的进程：** 收拾之前看这个用户在 logind 里的会话：
- 有**在线或活动**（`online`/`active`）的会话（同一个人在别处正登录着）：本次不收拾，只记一笔；在活着的会话底下挪文件会弄坏它。
  等他全部退出后的下一次登录再收拾。
- 只剩 `closing` 的会话（退出后还有残留进程，比如后台的 Chrome），或者 linger 留下的 `user@<uid>.service`：先 `disable-linger`，
  再 `terminate-user` 结束这些残留、停掉 `user@<uid>`，然后收拾。此时新会话还没注册（`pam_systemd` 在钩子之后），结束的只有旧的。
  否则学生只要留一个残留进程就能让收拾永远跳过。

**linger：** 学习模式下学生不该有常驻的用户管理器，否则它开机就起、在任何登录之前跑学生的用户服务（今天 polkit 只禁了访客自己开 linger）。
agent 在学习模式下每次应用与开机时，把非管理员账号的 linger 关掉（与 `lock` 步骤处理 linger 的方式一致）；登录钩子再兜一次。

**登录脚本（Group 的 `login` 脚本）：** 今天每个人每份脚本只成功跑一次（`login_queue` 记哈希）。学习模式下家目录每次登录都回到已知状态，
脚本写在保留清单之外的东西下次就没了，所以**学习模式设备上登录脚本每次登录都跑**（与访客相同）；完全模式照旧只跑一次。

**失败：** 收拾出错、超时、遇到异常条目时，**照样放行登录**，在回报里记一项（只有计数与原因类别，不写路径与名字），并在下一次登录重试。
理由见反目标第 2 条。作为第二道线，保留 2026-11-10 的两个环境生成器（只读 `session-mode`）：即使这次没收拾成，dconf 锁也不会被
用户的 environment.d 打开。`~/.pam_environment` 对所有设备关闭不变（PAM 已废弃，与学习模式无关）。

**范围的准确说法：** 钩子只在 GDM 的两个服务（`gdm-password`、`gdm-authd`）里。学习模式设备上没有别的登录入口（没有 SSH，tty 登录由
锁住的会话之外的机制管），用户管理器的另一个入口 linger 由上面一段关掉。

**学生看得到什么：** 什么都不提示。挪走的只是程序配置；学生自己的文件、Chrome、学校的应用都在。

### 不变式 4：完全模式

`session-mode` 是 full 或文件不在时，登录钩子不碰家目录，两个生成器原样交给发行版的生成器（今天已是如此）。

## 第二期：会话中的执行控制（只写范围）

- 目标：学习模式的会话里只能运行批准的程序（Chrome、批准的 Flatpak、桌面本身要的系统程序），其余被内核拒绝；对未知软件同样成立。
- 候选做法：给学习模式会话的进程套 AppArmor 配置（会话入口按 `session-mode` 选配置），或家目录与 `/tmp` 的 `noexec` 加解释器管控。
- 已知要解决的：`~/.local/share/applications` 里的启动器（Chrome 安装网页应用也写这里）、桌面需要的系统程序清单、Flatpak 的 bwrap。
- 单独出设计，VM 上磨允许清单。

## 约束

- 公开仓库；不写主机、账号、学校信息。注释与输出英文，用户可见文字（本设计预计没有）走 i18n。
- 登录路径上的代码必须有界、不阻塞登录过久；root 操作用户目录必须经 `safefs`。
- 回报与日志不写学生的文件名、路径与 uid（与 `homes` 一致）。

## 验证

- 单元测试：保留清单的判定（各种路径、大小写、符号链接、挂载点）、挪动只走 `safefs`、有界与超时、失败时放行、两个方向的模式写入次序、
  另有会话时不收拾、linger 的处理。
- check-tree：生成器只读 `session-mode`（不再看锁文件）。
- 重验证（另一个 session）：学习模式 VM 上放进 environment.d、`~/.profile`、自启动、systemd 用户服务、D-Bus 服务、shell 扩展，
  退出再登录后都不生效、学生文件与 Chrome 资料都在；完全模式 VM 上同样操作全部照常生效；模式从 full 切到 learning 再切回，
  `session-mode` 与锁始终一致。

## 留给实施者

- 收拾的条目数与耗时上限的具体值。
- 本机账号（如 IT 账号）与 `admin_users` 在学习模式设备上：默认同样收拾（锁本来就对它们生效），linger 只关非管理员的。
- `HomeCleanupJob` 的回收目录在登录路径上被使用时的命名与并发（与它每小时一轮的清空不冲突）。
- 学习模式设备上是否真的没有 tty 与 SSH 登录入口：核对一遍，有就把钩子也装上或在设计里补一句。

## 设计者的判断（未经 David 逐条确认）

- 收拾按"容器对调"做，耗时只与保留清单的长度有关。
- 同一个人另有在线会话时本次不收拾；只剩残留进程或 linger 时先结束它们再收拾。
- 学习模式下关掉非管理员的 linger。
- 学习模式设备上 Group 的登录脚本每次登录都跑。
- 放开到 full 时，只有与锁有关的步骤失败才挡住 `session-mode = full`。
- 保留清单加了屏幕排布、音量、文件选择框书签；学生自装网页应用的启动器不留。
- 出错照样放行登录，环境变量过滤留作第二道线。
